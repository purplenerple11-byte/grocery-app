# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

One person — the owner — using the app on their own phone. There is no second
audience: no admin, no household member, no guest. The owner is simultaneously
the shopper, the person who restocks the kitchen, and the person who decides
what the product becomes.

They use it in four distinct situations, all confirmed:

- **In-store, one hand, moving.** Pushing a cart, phone in one hand, checking
  items off and adjusting quantities while walking. Distraction is high,
  attention is partial, connectivity is unreliable.
- **At home, planning a trip.** Reviewing what's in stock, picking saved meals,
  building the list before leaving.
- **At home, restocking after.** Unpacking bags, correcting counts the trip loop
  got wrong.
- **Quick capture, anytime.** Noticing something has run out mid-week and adding
  it in a few seconds, from anywhere.

## Product Purpose

A personal grocery shopping list joined to a household inventory tracker. The
two screens are views of one `Item` record, so the list and the stock counts can
never disagree with each other.

Success is that the kitchen's real state and the app's state stay in sync
without the owner doing bookkeeping — they shop normally, and inventory updates
itself as a side effect.

## Positioning

The shopping-trip loop is the mechanism: completing a trip restocks inventory by
the quantity actually bought, deletes one-off items, and leaves unbought items
on the list. A list app and an inventory app bolted together cannot do this —
it works only because both screens read and write the same record, and because
the moment of truth (checkout) is also the moment of data capture.

## Operating Context

- Phone-first, installed to the home screen as a PWA; usable offline in a store.
- Deployed from `main` to GitHub Pages at
  https://purplenerple11-byte.github.io/grocery-app/ — **pushing to `main`
  publishes it** (~1 min). Repo: `github.com/purplenerple11-byte/grocery-app`.
- Run locally with `python3 -m http.server 8000` from the repo root (the service
  worker needs http, not `file://`).
- Tests run in a browser at `tests/run-tests.html`; use exactly one tab, since a
  second tab holds IndexedDB open and hangs the DB tests.
- Data lives only on the device. JSON export/import is the only backup, and the
  only way data moves between devices.

## Capabilities and Constraints

**Built and shipped:** shopping list with categories, check-off and quantity
stepper; inventory sheet with tile grid, status dots, and stock steppers; the
trip-completion loop; price + store history per item; saved meals with a
pre-flight modal for pruning; swipe-to-remove; collapsible inventory categories;
autocomplete on the quick-add field; strict restore and additive merge import;
JSON export; PWA install and offline shell.

**Technical constraints that are deliberate, not incidental:**

- Vanilla HTML/CSS/JS. **No framework, no npm, no build step, no ES modules** —
  plain `<script>` tags, so the test harness runs without a toolchain.
- `assets/store.js` stays pure: state-transition functions plus a thin IndexedDB
  adapter, with no DOM access. That purity is what makes it testable, so UI
  concerns must not leak into it.
- IndexedDB with write-through on every mutation; no save button. In-memory
  fallback plus a persistent banner when the DB is unavailable.
- `sw.js` caches the shell; its `CACHE` constant must be bumped whenever assets
  change, and the service worker will otherwise serve stale code.
- `icons/` is generated by `python3 tools/make_icons.py` and never hand-edited.

**Terminology (the app's own vocabulary, used in code and UI):**

- **Item** — the single record type; every screen is a view of it.
- **Tracked / untracked** — tracked items have a stock count and an inventory
  tile; untracked ones are one-offs that vanish when the trip completes.
- **On list / checked** — `onList` puts an item on the shopping list; `checked`
  means it is in the basket.
- **Stock, lowAt** — count on hand and the low-water threshold; status is
  derived, never stored (`0` = out, `<= lowAt` = low, else stocked).
- **Trip** — one shopping run, ended by "Complete trip", which is what restocks.
- **Meal** — a named set of item ids. It never copies item data, so renaming an
  item updates every meal and deleting one just drops it out.

**Explicitly undecided:**

- **Single-device is current, not permanent.** Today there are no accounts, no
  backend, and no sync, and none are planned. But the owner has flagged that a
  second device or sync is a plausible future direction — future work should not
  foreclose it. Treat local-only as today's constraint, not a principle.
- Categories are described in the spec as user-extendable, but editing an item
  whose category is outside `Store.CATEGORY_ORDER` still resets it to "Other".
- AI-generated *meals* carrying throwaway ids are not remapped on merge import.
- Export omits the `settings` key the spec mentions.

## Brand Commitments

- Name: **Grocery**. No logo or wordmark beyond the generated app icons.
- `docs/DESIGN.md` is the binding visual reference — the Anthropic "scientific
  field journal" parchment system. The app is a **deliberate dark inversion** of
  it, and that inversion is a decision, not drift: keep the warm earth-tone
  palette, serif for voice and sans for UI chrome, flat surfaces with hairline
  borders and no shadows.
- **Clay is reserved for action state only.** Stock status uses sage / ochre /
  clay-deep — never stock green, yellow, or red.

## Evidence on Hand

- The live deployment and the repository above are real and current.
- Real content is the owner's own grocery data in IndexedDB, portable only via
  JSON export.
- `docs/superpowers/specs/2026-07-16-grocery-app-design.md` is the approved
  design spec; `HANDOFF.md` carries the running record of shipped work and the
  decisions behind it.
- There are **no** users beyond the owner, no testimonials, no customers, no
  press, no benchmarks, no pricing, and no revenue. Future work must not invent
  any of these — there is no audience to persuade.

## Product Principles

1. **One record, two views.** The list and the inventory are the same data.
   Anything that lets them drift apart is a bug, not a feature.
2. **Bookkeeping is a side effect, never a chore.** The owner shops; the app
   updates itself. Never add a step whose only purpose is telling the app
   something it could infer from the trip.
3. **Usable while walking and distracted.** The in-store scene is the hardest
   one and it wins ties: reachable controls, forgiving targets, no state that
   punishes a mis-tap.
4. **The owner prunes; the app doesn't guess.** Where the app could infer intent
   — which meal items are needed, what to delete — it surfaces the choice rather
   than deciding silently. Destructive actions stay explicit.
5. **No toolchain, ever.** The absence of a build step is a feature of this
   project. A dependency that requires npm is disqualified regardless of merit.
